# Shadowrocket 两步导入记录

## 最终支持方式

Shadowrocket 把首页节点订阅和配置页原生配置保存为两个独立对象。单独导入任何一个都只能得到一半能力，因此页面必须提供严格有序的两步入口：

1. **首页节点订阅**：具名 HTTPS `.yaml` 地址；一键导入使用 `shadowrocket://add/<地址>`。它负责正确名称、节点刷新以及流量/到期横幅。
2. **配置页分流规则**：具名 HTTPS `.conf` 地址；一键导入使用 `shadowrocket://config/add/<地址>`。它负责规则、策略组、手动切换及原生 `DIRECT` / `REJECT`。

二维码同样分成两步：第 1 张在 Shadowrocket 首页扫码，第 2 张在「配置」页右上角扫码。页面默认展示第 1 步，并在切换第 2 步前持续提示“两步都要导入”。复制地址时也必须粘贴到对应入口，不能交叉使用。

## 真机验收结果

2026-09-23 的实机回归确认，两步都完成后可以同时获得：

- 用户填写的订阅名称；
- 可刷新的订阅节点；
- 流量、容量与到期横幅；
- 完整规则；
- `♻️ 手动切换`及其他策略组；
- 可选的原生 `DIRECT`；
- 广告和 NSFW 默认使用的原生 `REJECT`；
- 策略组嵌套与各组默认选择。

内置完整版、精简版、ACL4SSR 等第三方预设和允许的自定义远程配置均走同一转换链路。现代节点由 Mihomo 节点转换补回原生配置；具体协议能否连通仍取决于 Shadowrocket 自身版本与协议能力，不能由格式转换保证。

上游 `Subscription-Userinfo` 或完整 `STATUS=↑/↓/TOT/Expires` 会安全转换为用量响应头。首页节点订阅负责展示这些信息；配置页 `.conf` 负责原生策略语义。服务端同时向两条地址交付所需数据，但客户端不会把两个入口的 UI 与状态合并成同一个对象。

## 回归经过

- `site-v0.4.16` 的首页方案会生成两个条目，其中只有一个名称和横幅正确；
- `site-v0.4.19` 的首页方案导入了配置但没有节点；服务端多次返回 HTTP 200，仍不能证明客户端完成了节点导入；
- `site-v0.4.20` 将 provider 改为独立纯节点地址后，服务端确认主配置与节点响应均被成功请求，但首页仍没有节点；
- 完整 YAML 能稳定带来名称、节点和流量横幅，却不能让其中的 `DIRECT` / `REJECT` 成为 Shadowrocket 原生可选策略；
- 原生 `.conf` 从「配置」页导入后，规则、手动组和策略联动通过真机验证，但配置页本身不展示首页订阅横幅；
- 两条路径组合后，两边的已验证优点可以同时保留，且不再要求其中一个入口模拟另一个入口的语义。

这些结果说明“一条链接同时解决所有问题”不是服务端格式问题，而是 Shadowrocket 的对象模型边界。最终产品因此不再隐藏这个边界，而是把两个入口显式设计成一个两步流程。

## 自动化验证边界

测试会验证：

- 首页 `.yaml` 与配置页 `.conf` 都使用稳定名称，转换参数不会因嵌套 URL 丢失；
- 两个一键导入分别使用 `shadowrocket://add/` 与 `shadowrocket://config/add/`；
- 原生 `[Proxy]`、`[Proxy Group]`、`[Rule]` 均存在；
- 手动组以 `DIRECT` 开始，广告与 NSFW 组以 `REJECT` 开始；
- 首页地址透传用量元数据，现代节点补回、第三方配置和旧链接兼容行为不回归。

自动化只能验证服务端交付内容，不能替代 Shadowrocket 的 UI 与真机解析。以后修改任一导入路径或原生分组语法时，仍需在空状态下依次验收首页和配置页。诊断材料不得保存订阅查询串、token、节点密码、UUID 或设备标识。
