# Shadowrocket 导入边界与回归记录

## 验收目标

首页、配置页分别从空测试状态扫码一次：配置和节点均导入；首页只出现一份订阅，名称采用用户填写值，并保留上游提供的流量与到期横幅。重复扫码不新增副本。广告与 NSFW 默认 REJECT，手动切换分组可见。

## 已经取得的证据

- `site-v0.4.16` 的实机反馈：内联节点和独立 provider 会出现两个首页条目，其中 provider 条目具有正确名称和横幅。
- `site-v0.4.19` 的实机反馈：首页扫码安装了配置，但没有节点。服务端日志在 2026-09-22 11:25:15–11:25:53 UTC 记录到同一客户端对同一完整配置路径发起 26 次成功请求，单次约 520 KB；这与主配置的 provider 指回主配置形成循环相符。不能把 HTTP 200 或二次请求成功视为节点导入成功。
- [维护手册](https://github.com/LOWERTOP/Shadowrocket#添加节点)说明 URL fragment 可用来重复添加订阅，因此不能把 `#名称` 当成去重方案。
- [维护手册](https://github.com/LOWERTOP/Shadowrocket#配置文件)说明可从 Clash YAML 同时导入节点和配置，但未给出两个扫码入口对空节点列表及 provider 的完整解析规范。

## 当前输出契约

完整 YAML 保留规则、策略组和显式的 `proxies: []`，节点仅由一个按用户名称命名的 HTTP provider 提供。这里的空数组是有效 YAML 列表，不能删掉整个字段，也不能写成没有值的 `proxies:`（其 YAML 值是 null）。首页对该空数组的处理尚需真机验收，不将其写成已经验证的客户端行为。

无状态 provider 地址为 `/i/<名称>.nodes.yaml?...&srnodes=1`；存档模式为 `/sub/<id>/nodes`。二者只返回非空 `proxies` 列表，不含规则、策略组或下级 provider；都携带相同名称和订阅用量响应头。配置 URL 和节点 URL 必须不同，依赖只走一层。

## 验证边界

`e2e-local.mjs` 实际请求主配置及其声明的节点地址，再调用 `check-shadowrocket-import.py` 解析两份 YAML：检查空本地列表、唯一具名来源、无环且终止的节点响应、现代协议保留、策略组引用、广告/NSFW 默认值和完整规则。主配置自引用、provider 中出现下级 provider，以及内联重复节点，都必须失败。

这些检查验证服务器交付的数据与依赖关系，不等于运行了 Shadowrocket。两个扫码入口的最终 UI 结果需要真机确认；若不符，应按扫码时间核对无查询串的访问日志，区分主配置请求与节点请求。不要保存订阅查询串、凭据或设备标识作为诊断材料。
