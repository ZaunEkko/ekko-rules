# Shadowrocket 导入边界与回归记录

## 验收目标

首页、配置页分别从空测试状态使用各自的二维码扫码一次：配置和节点均导入。首页入口优先保证节点与规则一次导入，接受订阅名称由客户端显示为站点域名；配置页入口保留用户填写名称及上游流量与到期横幅。广告与 NSFW 默认 REJECT，手动切换分组可见。

## 已经取得的证据

- `site-v0.4.16` 的实机反馈：内联节点和独立 provider 会出现两个首页条目，其中 provider 条目具有正确名称和横幅。
- `site-v0.4.19` 的实机反馈：首页扫码安装了配置，但没有节点。服务端日志在 2026-09-22 11:25:15–11:25:53 UTC 记录到同一客户端对同一完整配置路径发起 26 次成功请求，单次约 520 KB；这与主配置的 provider 指回主配置形成循环相符。不能把 HTTP 200 或二次请求成功视为节点导入成功。
- `site-v0.4.20` 把 provider 改成独立纯节点地址；2026-09-22 12:52:07–12:52:08 UTC 的服务端日志确认真机依次成功取到完整配置与纯节点响应，但实机首页仍未生成节点。由此确认首页不能依赖 provider，即使两次 HTTP 请求均为 200。
- [维护手册](https://github.com/LOWERTOP/Shadowrocket#添加节点)说明 URL fragment 可用来重复添加订阅，因此不能把 `#名称` 当成去重方案。
- [维护手册](https://github.com/LOWERTOP/Shadowrocket#配置文件)说明可从 Clash YAML 同时导入节点和配置，但未给出两个扫码入口对空节点列表及 provider 的完整解析规范。

## 当前输出契约

两个扫码入口使用不同 HTTPS 地址与不同响应，页面必须先选择入口：

- 首页地址带 `srhome=1`，完整 YAML 内联非空 `proxies`、策略组与规则，不包含 `proxy-providers`。这是恢复已经通过真机的形状，已知取舍是首页订阅名称可能显示为 `sub.boxnook.cc`。
- 配置页地址带 `srconfig=1`，完整 YAML 保留规则、策略组和显式 `proxies: []`，节点由一个按用户名称命名的 HTTP provider 提供，以保留正确名称和流量横幅。

无状态配置页 provider 地址为 `/i/<名称>.nodes.yaml?...&srnodes=1`；存档模式为 `/sub/<id>/nodes`。二者只返回非空 `proxies` 列表，不含规则、策略组或下级 provider；都携带相同名称和订阅用量响应头。配置页 URL 和节点 URL 必须不同，依赖只走一层。首页地址不请求这条 provider。

## 验证边界

`e2e-local.mjs` 会分别请求首页内联配置、配置页 provider 配置及其节点地址，再调用 `check-shadowrocket-import.py` 解析 YAML：首页必须有非空内联节点且无 provider；配置页必须有空本地列表、唯一具名来源及无环终止的节点响应。两条路径都检查现代协议、策略组引用、广告/NSFW 默认值和完整规则。

这些检查验证服务器交付的数据与依赖关系，不等于运行了 Shadowrocket。两个扫码入口的最终 UI 结果需要真机确认；若不符，应按扫码时间核对无查询串的访问日志，区分主配置请求与节点请求。不要保存订阅查询串、凭据或设备标识作为诊断材料。
