# Shadowrocket 原生导入记录

## 最终支持方式

Shadowrocket 使用具名原生 `.conf`。页面只提供一套入口：

- 二维码是普通 HTTPS `.conf` 地址，必须在 Shadowrocket 的「配置」页右上角扫码；
- 「一键导入 Shadowrocket 配置」使用 `shadowrocket://config/add/<同一地址>`；
- 复制地址后也应在「配置」页导入；
- 不支持从首页扫码。首页会把地址当作节点订阅，无法建立原生 `DIRECT` / `REJECT` 策略联动。

历史 `srhome=1` YAML 路由继续保留，防止已经导入的旧远程地址突然失效；当前页面不会再生成或推荐它。

## 真机验收结果

2026-09-23 的实机回归确认，配置页导入具名 `.conf` 后可同时获得：

- 用户填写的配置名称；
- 订阅节点；
- 完整规则；
- `♻️ 手动切换`及其他策略组；
- 可选的原生 `DIRECT`；
- 广告和 NSFW 默认使用的原生 `REJECT`；
- 策略组嵌套与各组默认选择。

内置完整版、精简版、ACL4SSR 等第三方预设和允许的自定义远程配置均走同一转换链路。现代节点由 Mihomo 节点转换补回原生配置；具体协议能否连通仍取决于 Shadowrocket 自身版本与协议能力，不能由格式转换保证。

上游 `Subscription-Userinfo` 或完整 `STATUS=↑/↓/TOT/Expires` 可被安全转换为用量响应头。Shadowrocket 的「配置」页不显示首页节点订阅样式的流量横幅，因此最终产品选择保证完整规则和原生策略联动，而不是保留一个功能不完整的首页入口。

## 回归经过

- `site-v0.4.16` 的首页方案会生成两个条目，其中只有一个名称和横幅正确；
- `site-v0.4.19` 的首页方案导入了配置但没有节点；服务端多次返回 HTTP 200，仍不能证明客户端完成了节点导入；
- `site-v0.4.20` 将 provider 改为独立纯节点地址后，服务端确认主配置与节点响应均被成功请求，但首页仍没有节点；
- 后续完整 YAML 能带来流量横幅，却不能让 YAML 中的 `DIRECT` / `REJECT` 成为 Shadowrocket 的原生可选策略；同语义代理别名也不能等价替代；
- 原生 `.conf` 从「配置」页导入后，名称、节点、规则和策略联动最终通过真机验证。

这些结果说明 Shadowrocket 的首页订阅与原生配置是两个不同的产品入口。一个远程地址即使内容中同时写有节点和规则，也不能迫使首页扫码器按原生配置语义注册它。

## 自动化验证边界

测试会验证：

- `.conf` 地址使用稳定名称且转换参数不会因嵌套 URL 丢失；
- 一键导入使用 `shadowrocket://config/add/` 包裹同一 `.conf` 地址；
- 原生 `[Proxy]`、`[Proxy Group]`、`[Rule]` 均存在；
- 手动组以 `DIRECT` 开始，广告与 NSFW 组以 `REJECT` 开始；
- 现代节点补回、第三方配置、用量字段与旧链接兼容行为不回归。

自动化只能验证服务端交付内容，不能替代 Shadowrocket 的 UI 与真机解析。以后修改导入路径或原生分组语法时，仍需在空状态下从「配置」页重新扫码验收。诊断材料不得保存订阅查询串、token、节点密码、UUID 或设备标识。
